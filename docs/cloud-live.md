# ライブ収集のクラウド移行案

2026-11-07 時点。GitHub Pages は公開フロント、Sites 上の Worker と D1 は中央の読み取り・履歴 API。取得元を巡回する Node.js 24 の収集プロセスと送信プロセスは Windows PC 上で動く。地方は同じ PC 内の表示・保存を使う。GitHub Actions はテストと Pages 公開を行う。 [現在の接続構成](live-connection.md) · [地方の起動手順](nar.md)

## 更新周期を三つに分ける

| 段階 | 現状 | 移行時の方針 |
| --- | --- | --- |
| 公式Webに新しい値が出る | 中央と地方の発表表示は分精度。応答内の価格や発表表示がいつ変わるかは別々に実測する | 発表時刻、価格ハッシュ、キャッシュ情報、取得元の異常を記録する |
| サーバーが公式Webを取りに行く | 締切前は約10秒。中央の自動巡回は場を順番に取得し、地方は並行取得。応答待ちのため実受信間隔は伸びる | まず10秒を維持。場ごとに開始時刻を管理し、同じ場でリクエストを重ねず、遅い場が他場を待たせない構成にする |
| ブラウザーに反映する | 中央は約2秒ごとに送信プロセスが出力を確認し、ブラウザーは応答終了から1秒後に次のGETを開始 | 受信済みの新着を差分で配信し、受信から画面までの遅延を計測する |

### 保存データの比較

2026-11-07 の単勝の観測。複勝は同じレスポンスで取得した。時刻は JST。締切はいずれも投票サービスの通常規則に基づく予定時刻。

| レース | 対象区間の受信 | 異なる発表表示 | 最後の受信 | その値の発表表示 |
| --- | ---: | ---: | --- | --- |
| 東京10R | 55回／10分 | 11種類 | 14:59:53.661（締切6.339秒前） | 14:59 |
| 帯広ば11R | 31回／約6分 | 7種類 | 19:57:57.077（締切2.923秒前） | 19:57 |

受信回数は価格更新回数と区別する。発表の分表示が同じまま価格が変わった応答も保存されている。分表示のため、公式側の更新秒や投票の反映遅延はこのデータから確定できない。東京7Rでは約3.5秒前に受信した値の発表表示が、予定締切の2分前だった。 [東京7Rの測定](live-measurement-2026-11-07.md)

### 10秒・5秒・1秒

| 試行周期 | 1レース10分／36レース | 判断 |
| --- | ---: | --- |
| 10秒 | 約60回／2,160回 | 常駐収集の初期値。現行パーサーとデータ契約で再計測 |
| 5秒 | 約120回／4,320回 | 取得元の条件を確認して1場・短時間で比較。10秒では拾えない価格更新、または実用的な先行受信が増える場合に拡大 |
| 1秒 | 約600回／21,600回 | 公式Webの新しい値を1秒で得られる根拠は未確認。まず自前の配信を高速化し、公式側は秒単位の配信と利用条件を確認できる経路で再評価 |

試算は単複共通の1リクエストを単位とし、出馬表・日程・失敗の再試行を除く。理想化した一定間隔で更新の発生位相が一様なら、10秒から5秒にして縮まる待ち時間は平均2.5秒。公式側の遅れは別に残る。

現行の中央APIで測った1応答は3場で約650 KB（展開後）。同サイズを毎秒取り直すと、1人でも1時間あたり約2.34 GB相当のJSONを処理する。中継の書き込みにも約150万文字の上限がある。ライブでは初回と再接続時に全体を返し、続きは観測の差分をSSEで送る。価格が同じ受信でも、受信時刻と30秒値を正しく更新できるよう観測の有無を送る。接続維持通知は観測とは別にする。 [SSE仕様の解説](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)

## フロントとバックエンドの組み合わせ

| 構成 | 適性 |
| --- | --- |
| GitHub Pages ＋ 日本リージョンの常駐Node.js ＋ 現行API | 第一候補。PagesのURL、パーサー、SQLite、公開APIを再利用できる。収集だけ先に移して10秒を検証し、配信は次に差分化。Linux VPS の価格例は、さくらのVPS 東京 1GB が月払い990円。メモリとディスク使用量は実測で決める。 [さくらのVPS料金・仕様](https://vps.sakura.ad.jp/specification/) |
| GitHub Pages ＋ 常時起動のコンテナ ＋ 永続ボリューム | VPSの運用を減らしたい場合の候補。Fly Machinesには東京リージョンがあり、Nodeのコンテナと永続ボリュームを使える。観客がいない間も収集するため、トラフィック連動の自動停止を無効にする。料金はリージョン・稼働・ボリューム・転送で確認する。 [Flyのリージョン](https://docs.fly.io/reference/regions/) · [自動停止](https://docs.fly.io/launch/autostop-autostart/) · [料金](https://www.fly.io/docs/about/pricing/) |
| GitHub Pages ＋ Workers／Durable Objects | Cronの最小単位は分。Durable Objectsのアラームはより細かく設定できるが、失敗時の再試行や秒単位の実行間隔を測る必要がある。既存のローカルSQLite・生バイト保存を移す作業もあるため、初回の収集移行より配信側の候補。 [Cron](https://developers.cloudflare.com/workers/configuration/cron-triggers/) · [Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/) |
| GitHub Pages ＋ GitHub Actionsのみ | Pagesは静的配信。Actionsの定期起動は最短5分で、混雑時に遅延・取りこぼしがある。起動済みのジョブ内で10秒ループは可能だが、定時起動と永続ストレージを別に解決する必要がある。ActionsはCIとデプロイに使う。 [Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site) · [定期起動の仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onschedule) · [定期起動の制約](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) |

## 移行の順序と確認条件

1. 候補ホストで公式応答を取得できるか確認する。中央のShift_JIS、地方のUTF-8、複数開催の自動検出、予定発走変更と取消を照合する。公開範囲、取得周期、保存期間を各提供元の条件に合わせる。地方の公開配信は許諾確認後に行う。中央についても既存の接続実績とクラウドでの取得・配信条件を区別して確認する。 [JRAの利用案内](https://www.jra.go.jp/use/) · [地方競馬情報サイト利用規約](https://www.keiba.go.jp/terms.html)
2. PCの代わりにホスト上でNode.js 24を常駐させる。専用ユーザーと自動再起動を設定し、SQLiteと観測ファイルはリリース外の永続領域に置く。送信キーはホストの秘密設定に渡す。旧プロセスと新プロセスが同じ配信先に同時送信しない状態で切り替え、直前のコミットに戻せるようにする。
3. 複数場の締切前10分を観測する。取得開始、受信、発表表示、予定締切、配信受理、描画を別々に計測する。取得失敗、発表の逆行、最大受信間隔、締切前の最後の新着を記録する。初期目標は受信間隔のp95が15秒以内、直前5分に30秒超の欠損がないこと。締切後・最終値は混ぜない。
4. 全体JSONから差分配信に移し、受信から描画までp95で2秒以内を目標にする。再接続で欠けた更新は全体取得で復元し、配信停止時は古さを表示する。地方は当面、必要に応じて認証付きの同一オリジン画面で検証する。公開版の静的JavaScriptには鍵を含めない。
5. 5秒試験は同一ストリームから10秒相当の系列も作り、直前5分の追加の新着、先行時間、タイムアウト・拒否率を比較する。取得元のエラーや流量制限が増えたら戻す。秒単位の公式配信が確認できた場合は、同じ時刻契約で1秒取得を検証する。

この文書の段階では既存の公開構成で運用中。サーバー契約とクラウドへの収集移設は、候補の接続と利用条件を確認してから行う。
